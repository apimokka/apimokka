# apimokka v0.1.0 — RFC Audit

**Date:** 2026-05-22
**Auditor:** post-implementation review
**Scope:** All 18 RFC-MK documents from the upstream RFC package.

---

## Summary

Only **5 of 18** RFCs were written into `rfcs/done/` before this audit. The
code itself implements roughly **11 of 18** at meaningful fidelity, **4 of 18**
partially, and **3 of 18** not at all. The previous CHANGELOG/README
implication that "the implementation is complete" was inaccurate.

This document corrects the record per-RFC and lists exactly what was deferred.

## What "Implemented" actually means here

For this audit, an RFC counts as Implemented when:
1. The mockup screens or behaviours named in its acceptance criteria are present in code.
2. The corresponding messages and state transitions exist in `app.rs`.
3. A real user could exercise the flow end-to-end inside the mockup,
   accepting mock-quality fidelity (canned data, no real I/O).

It does **not** mean:
- Production-grade error handling
- Real file I/O or network calls
- Pixel-perfect adherence to a visual design spec
- Verified accessibility against assistive technologies

## The three gaps that need work

### 1. MK-013 — Match-test workflow (P1)

Required surfaces:
- `Test this rule` button in the rule builder
- `Replay as test input` action on trace events
- Result panel showing per-condition pass/fail

Status: **Nothing in code**. The original `Message::Noop` and `Key::BtnTestRule`
exist as scaffolding but no panel, dialog, or even disabled button surfaces them.

### 2. MK-015 — Keyboard contract (P0)

Acceptance criterion: *All primary workflows can be completed without a pointer.*

Current state:
- ✅ Non-color status (glyphs everywhere)
- ✅ Command palette dialog
- ✅ Tooltips on left rail
- ❌ No `iced::keyboard::on_key_press` subscription
- ❌ Cmd+K / Ctrl+K does nothing
- ❌ Tab order not verified
- ❌ No focus ring style hooks

iced 0.14 provides `Subscription::events_with` and `iced::keyboard::on_key_press`
helpers that would be needed.

### 3. MK-016 — Non-destructive safety (P1)

Required:
- File watcher notification when TOML edited externally
- Undo/redo on `EditCommand` log
- Confirmation dialog for destructive actions (Delete rule set, Clear all headers, etc.)
- Honest disclosure of undo session scope

Status: **Nothing in code**. Destructive actions fire immediately on click.

## What was correctly documented

The 5 RFCs filed (MK-000, 001, 003, 007, 015) reflect real implementation
work. MK-015's RFC document is the one that overstates progress — it should
say "Partial — keyboard handling deferred."

## Recommended remediation

In order of cost / value:

1. **Write the 13 missing RFC documents** with honest status. ~30 minutes.
   This restores the audit trail without changing code.
2. **Add destructive-action confirmation** (MK-016). Single shared dialog
   pattern. ~2 hours.
3. **Wire the keyboard subscription** (MK-015): Esc to close drawer/palette,
   Cmd+K to open palette, Tab cycling between major regions. ~3 hours.
4. **Implement the Test-Rule panel** (MK-013): a side dialog opened from
   the rule builder with input fields and a stub pass/fail result.
   ~3 hours.
5. **Add file-route promote-to-rule** (MK-005): right-click "Promote to rule"
   action that creates a new rule with `url_path` = the file's route hint
   and `respond.file_path` = the file. ~1 hour.

Items 1-2 fit in one session; 3-5 fit in another.

---

## Lesson for the record

Claiming "Phase 1 complete" without per-RFC acceptance-criteria verification
is exactly the failure mode that RFC-MK-000 §"silent withdrawal" warns
against. The fix going forward: before marking an RFC `Implemented`, copy
its acceptance criteria into a checklist and tick each one against the
code, not against memory.
