# RFC MK-053 — Integration boundary and workspace adapter

**Status.** Proposed
**Tracks.** Stabilization roadmap M3 — Integration boundary.
**Touches.** Mock workspace ownership, edit intents and engine-command mapping,
snapshot refresh and selection, stable condition identity, diagnostics and
runtime hints, undo/redo, app reducer seams and tests, model documentation.

## Summary

Adopt an **explicit UI mapping** boundary rather than claiming the current
mockup model is engine-isomorphic. The app will dispatch typed UI edit intents
to a `WorkspacePort`; an in-memory implementation will map those intents to the
editing semantics documented by the apimock-rs 5.10.1 GUI integration
reference, apply them to owned workspace state, and return a fresh read-only
snapshot plus typed effects.

The 5.10.1 reference is the intended production contract, but no reproducible
5.10.1 `apimock-config` artifact is currently available. M3 can therefore prove
the local boundary and every documented conversion; it cannot claim binary or
source conformance to an unavailable library. A future production adapter must
implement the same port and pass the same contract suite against an explicitly
adopted engine artifact.

Before adapter behavior changes, inline `app.rs` test modules move to the
project-required external test-file structure. This is a mechanical preparation
slice, not general M5 cleanup.

## Context

The integration reference requires a snapshot/apply lifecycle: the GUI renders
`WorkspaceSnapshot`, dispatches `EditCommand`, handles `ApplyResult`, and then
re-snapshots. `NodeId` values remain stable within one workspace session and
are regenerated by a new load.

The mockup currently mutates `WorkspaceSnapshot` throughout `App::update` and
undo helpers. Its model comments say the types mirror or map directly to the
engine, but material differences make that claim unsafe:

| Surface | Mockup today | 5.10.1 reference |
|---|---|---|
| Rule optional fields | empty strings / plain vectors | `Option` fields with update semantics |
| Header/body collections | `Vec<T>` | `Option<Vec<T>>`: preserve / clear / replace |
| Condition identity | rule ID plus vector index | stable condition `NodeId` |
| Body expected value | `String` | `serde_json::Value` |
| Header expected value | `String` | optional for presence operators |
| Response | mode plus always-present fields | independent optional text/file/status/delay with validation |
| Per-rule strategy data | weight and priority in mock payload | described by reference prose but omitted from its shown `RulePayload` |
| Root settings | includes trace controls | shown `RootSettingKey` omits trace keys |
| Apply result | declared but unused | changed nodes, diagnostics, reload effect |
| Undo/redo | direct snapshot mutation; Add redo incomplete | GUI-owned compensating commands over `apply` |

The mismatch already produces dishonest behavior: most edits bypass
`EditCommand`, condition commands address shifting indices, Add Rule redo is a
silent no-op, and simulated autosave clears dirty flags without an adapter save
boundary.

## Goals

1. Put all configuration mutations behind one testable workspace boundary.
2. Document and test every non-isomorphic UI-to-reference conversion.
3. Give header and body conditions stable session-scoped `NodeId` values.
4. Preserve the reference's collection update distinction: preserve, clear,
   and replace.
5. Refresh snapshots after successful applies without losing valid selection.
6. Represent apply errors, diagnostics, changed nodes, reload, and restart
   effects explicitly.
7. Make undo/redo complete for the supported command set, including Add Rule
   and Add Rule Set, without pretending recreated nodes retain deleted IDs.
8. Define manual reload/external-edit and session-lifetime boundaries for later
   production integration.
9. Remove unsupported “direct mirror” compatibility claims from model docs.

## Non-goals

- Link an unavailable `apimock-config` 5.10.1 crate or copy its implementation.
- Load or save real TOML, watch files, merge external edits, or run a server.
- Implement trace sockets, helper-process control, or production persistence.
- Change Test Rule matcher semantics adopted by MK-052.
- Redesign screens, routes, fixtures, general module layout, or all oversized
  files; M5 owns broad structural cleanup.
- Promise identity stability across workspace loads or restored sessions.
- Implement multi-user editing or conflict merging.
- Create a release, commit, tag, archive, or push.

## Decision

### 1. Explicit UI mapping, not isomorphism

The app-facing contract uses UI concepts deliberately:

```rust
pub trait WorkspacePort {
    fn snapshot(&self) -> PortSnapshot;
    fn apply(&mut self, transaction: EditTransaction) -> Result<EditOutcome, ApplyFailure>;
    fn validate(&self) -> ValidationReport;
    fn save(&mut self) -> Result<SaveOutcome, SaveFailure>;
}

pub struct EditOutcome {
    pub snapshot: PortSnapshot,
    pub changed_nodes: Vec<NodeId>,
    pub creations: Vec<CreationReceipt>,
    pub rebound_nodes: Vec<NodeRebind>,
    pub unsaved_hint: ReloadHint,
}
```

`EditTransaction` is a nonempty ordered list of `EditIntent`s applied
all-or-nothing. Validation occurs against a private candidate workspace; only a
fully successful transaction replaces port state. `RestoreSubtree` is a typed
intent carrying an archived semantic rule-set or rule tree and its former IDs.
It is used only for compensation and is still subject to normal validation.
Production adapters that cannot provide transactional apply must stage against
an isolated engine workspace and commit only the validated result; otherwise
they do not implement this port.

Every create intent carries a transaction-local `SemanticCreationKey`. Keys are
unique within the transaction and describe position, not content, for example
`rule-set`, `rule-set/rule[1]`, and `rule-set/rule[1]/body[2]`. Therefore two
equal conditions remain distinguishable. Results are typed:

```rust
pub struct CreationReceipt {
    pub key: SemanticCreationKey,
    pub kind: NodeKind,
    pub parent: Option<NodeId>,
    pub new_id: NodeId,
}

pub struct NodeRebind {
    pub old_id: NodeId,
    pub kind: NodeKind,
    pub new_id: NodeId,
}
```

Ordinary adds return receipts. A restore returns receipts plus exactly one
`NodeRebind` for every archived node, including all conditions in the subtree.
Missing, duplicate, wrong-kind, or non-bijective correlations fail the entire
transaction. A future adapter may derive receipts from before/after snapshots
only when the semantic keys make that derivation unique; it may never correlate
by structural equality alone.

The port is object-safe or enum-dispatched and owned by one `WorkspaceSession`.
Screens never receive mutable workspace state. `App` may cache the latest
snapshot for rendering, but only the port can replace it after apply/save/load.

#### 1.1 Port snapshot and condition identity amendment (2026-07-17)

Implementation inspection after the boundary-types checkpoint found that the
legacy render `WorkspaceSnapshot` embeds header/body payloads without condition
IDs. Returning it directly from `WorkspacePort` makes the accepted ID-based
condition update/remove intents unusable for conditions present at session
load. The separately defined `RuleConditionsView` was not reachable through
the committed trait.

The port therefore returns a sealed transition wrapper rather than changing or
duplicating fields inside the legacy render types:

```rust
pub struct PortSnapshot {
    workspace: WorkspaceSnapshot,
    rule_conditions: Vec<RuleConditionsEntry>,
}

pub struct RuleConditionsEntry {
    rule_id: NodeId,
    conditions: RuleConditionsView,
}
```

Read-only accessors expose the render workspace, the ordered condition entries,
and lookup by rule ID. `into_legacy_workspace` may be used only where ownership
of the legacy render snapshot is required during migration; its name documents
that condition identity is deliberately discarded. Callers cannot construct or
mutate wrapper entries. The in-memory port builds both views from one private
canonical state; the legacy payload vectors are projections for existing
screens, not a second mutable source of truth.

There is exactly one entry per rule, in rule-set/rule presentation order. No
entry names an absent rule. Condition IDs are unique across the entire session
node domain and the canonical values in each entry project to the corresponding
legacy payload order according to the normalization contract below. One private
snapshot-construction routine creates both views and makes consistency true by
construction; contract tests independently verify the invariants. Later reducer
slices cache `PortSnapshot`, render through `workspace()`, and address condition
edits through `conditions(rule_id)`. This additive transition seam avoids
rewriting screens in the adapter slice and can disappear when the legacy render
payload is retired.

Canonical condition state does not retain the user's original draft bytes.
Legacy render payloads use these two exhaustive projection functions:

```rust
fn project_header_condition(value: &HeaderCondition) -> HeaderConditionPayload;
fn project_body_condition(value: &BodyCondition) -> BodyConditionPayload;
```

The projection is deterministic and operator-specific:

| Canonical field/family | Legacy projection |
|---|---|
| header name | canonical lowercase `HeaderName::as_str()` |
| header operation | unchanged operation |
| value-bearing header expected value | stored string, including empty |
| header Exists / Absent | empty string |
| body path and operation | unchanged path and operation |
| Equal, EqualString, Contains, StartsWith, EndsWith, Regex | underlying JSON string without JSON quoting |
| EqualTyped, ArrayContains | canonical compact JSON defined below |
| EqualNumber, GreaterThan, LessThan, GreaterOrEqual, LessOrEqual | stored `serde_json::Number::to_string()` |
| EqualInteger | stored signed JSON integer `Number::to_string()` |
| ArrayLengthEqual, ArrayLengthAtLeast | stored unsigned JSON integer `Number::to_string()` |
| body Exists / Absent | empty string |

Canonical compact JSON is serialized recursively with no insignificant
whitespace: null/booleans use JSON literals, strings use `serde_json` JSON
escaping, arrays preserve element order, object keys are sorted by their UTF-8
byte sequences at every nesting level, and numbers use
`serde_json::Number::to_string()`. Sorting is explicit and does not depend on
the map implementation or enabled `serde_json` features. Canonical values
exclude non-finite numbers, so this projection is total.

Projection followed by the accepted draft-to-canonical mapping must reproduce
the same canonical condition for every operator. It need not reproduce the
original draft bytes. For example, `X-Request-ID` projects as `x-request-id`,
`1.5e2` projects as the exact stored `Number::to_string()` result rather than
retaining exponent spelling, formatted or differently key-ordered typed JSON
projects as sorted compact JSON, and every presence value projects as an empty
string. If exact draft preservation is later required for an active editor,
the draft is app-owned presentation state and is never inferred from canonical
workspace data.

### 2. Boundary types, provenance, and conversion contract

`EditIntent` expresses user intent without overloading empty values:

- rule-set add/remove;
- rule add/update/delete/move;
- response update;
- root setting update for reference-backed keys;
- header/body add/update/remove by condition `NodeId`; and
- explicit collection replacement using `CollectionEdit<T>`.

```rust
pub enum CollectionEdit<T> {
    Preserve,
    Clear,
    Replace(Vec<T>),
}
```

The boundary distinguishes three provenance classes:

| Class | Meaning |
|---|---|
| Documented Reference | Stated by the 5.10.1 GUI integration reference |
| Local M3 Decision | Deterministic mock/port behavior required here, not an engine-equivalence claim |
| ReferenceGap | No usable command representation is established; excluded from workspace edits |

The common conversion contract is:

| Surface | Conversion | Provenance |
|---|---|---|
| collection Preserve / Clear / Replace | `None` / `Some(vec![])` / `Some(values)` | Documented Reference |
| empty URL draft | `url_path: None`, `url_path_op: None` | Local M3 Decision |
| nonempty URL draft | `Some(value)` and selected operator | Documented Reference |
| Any / constrained method | `None` / `Some(value)` | Documented Reference |
| header Exists/Absent | expected value `None` | Local M3 Decision; payload type absent from reference |
| other header operation | expected value `Some(text)` | Local M3 Decision; payload type absent from reference |
| response inline / file | exactly one of text/file is `Some` | Local M3 Decision consistent with reference optionals |
| blank optional status/delay | `None` | Local M3 Decision |

Nonempty URL drafts accept exactly Equal, StartsWith, Contains, EndsWith,
WildCard, or NotEqual. Method accepts Any as `None`, or the uppercase GET,
POST, PUT, and DELETE labels shown by the reference as `Some(label)`; other
labels are typed failures. A body path is one or more nonempty dot-separated
UTF-8 components with no NUL; leading/trailing dots, empty components, and a
leading `$` component are rejected. This is the reference's dotted mini-syntax,
not JSONPath; treatment of object keys that themselves contain dots remains a
`ReferenceGap` and the M3 editor cannot address them.

Header names are parsed with `http::HeaderName`; invalid names are rejected and
accepted names are stored in the parser's lowercase canonical form. Empty
expected text is valid for all non-presence header operators. The supported
header families are Equal, Contains, StartsWith, EndsWith, Regex, Exists,
Absent, NotEqual, and WildCard; each has a mapping test.

Body payloads use `Option<serde_json::Value>` locally because the reference
does not show `BodyConditionPayload`. Exists and Absent use `None`. The other
operator families have these complete grammars:

| Body family | Accepted draft and canonical value | Provenance |
|---|---|---|
| Equal, EqualString, Contains, StartsWith, EndsWith, Regex | any UTF-8 draft, including empty; `Value::String(draft)` | Local M3 Decision |
| EqualTyped, ArrayContains | exactly one complete JSON value with optional surrounding JSON whitespace | Local M3 Decision |
| numeric comparisons | exactly one JSON number, convert to finite `f64`, then `Number::from_f64` | Local M3 Decision |
| EqualInteger | `0` or optional `-` plus a nonzero ASCII digit followed by digits; parse to signed 64-bit JSON integer | Local M3 Decision |
| ArrayLengthEqual, ArrayLengthAtLeast | `0` or a nonzero ASCII digit followed by digits; parse to `usize`, then JSON unsigned integer | Local M3 Decision |
| Exists, Absent | draft must be empty; canonical expected value `None` | Local M3 Decision; payload type absent from reference |

Leading `+`, leading zeroes except `0`, exponent/fraction forms for integer and
length operations, overflow, non-finite values, trailing input, and wrong JSON
types are typed field failures. Numeric JSON syntax may include fraction or
exponent forms. Operation names are matched exhaustively so a new operator
cannot silently take a default branch.

Response drafts map as follows. Inline mode accepts any UTF-8 text, including
empty, and clears file path. File mode requires a nonempty workspace-relative
UTF-8 path using the lexical component rules in section 3 and clears text.
Status is blank or three ASCII digits in `100..=599`, optionally followed by a
single space and nonempty display reason. The accepted nonblank string is
preserved canonically; the numeric prefix controls validation.
Delay is blank or ASCII digits parsed to `u64` milliseconds; blank is `None`
and `0` is `Some(0)`. A payload with both or neither text/file option selected,
invalid status, delay overflow, or invalid file path is rejected atomically.

Every reference-backed root key has one accepted value shape:

| Root key | `EditValue` and validation | Runtime effect |
|---|---|---|
| ListenerIpAddress | String; nonempty IP literal | Restart |
| ListenerPort | Integer `1..=65535` | Restart |
| ServiceStrategy | Enum `FirstMatch`, `UniformRandom`, `WeightedRandom`, `Priority`, or `RoundRobin` | Reload |
| ServiceFallbackRespondDir | String; empty or valid relative directory path | Reload |
| TlsEnabled | Boolean | Restart |
| TlsCertFile, TlsKeyFile | String; empty or valid relative file path | Restart |
| LogLevel | Enum `error`, `warn`, `info`, `debug`, or `trace` | Reload |
| LogFormat | Enum `plain` or `json` | Reload |
| LogFile | String; empty or valid relative file path | Restart |
| FileTreeShowHidden, FileTreeBuiltinExcludes | Boolean | Reload |
| FileTreeExtraExcludes, FileTreeInclude | StringList; preserve order, reject empty items | Reload |

The key catalog and reload/restart association are Documented Reference; the
precise local validation and `EditValue` variants are Local M3 Decisions.
Unknown keys and mismatched value variants are typed failures. Weight,
priority, and trace settings remain `ReferenceGap` because the reference omits
their usable command representation. Strategy seed and priority-tiebreaker
parameters are also `ReferenceGap`; M3 preserves only the five UI strategy
labels and makes no engine-default claim.

The UI may keep text drafts needed by widgets, but drafts are not snapshots and
cannot be described as engine payloads. Draft parsing failures leave port state
and all history unchanged and produce a typed field failure. Silently mapping
any field through a free-form string key is forbidden.

### 3. Stable identity and rule-set path contract

Port snapshots expose per-rule condition views containing:

```rust
pub struct ConditionWithId<T> {
    pub id: NodeId,
    pub condition: T,
}
```

Header/body update and remove intents use the condition ID, never an index.
Order remains presentation data and may change after load. The in-memory
workspace maintains IDs across snapshots, rule moves, unrelated edits, saves,
and updates of the condition itself. Adding creates a fresh ID; removing
invalidates it.

IDs are UUID-backed, unique across every editable node in one session, absent
from serialized payloads, and invalid after session reload. Tests enumerate the
complete snapshot to prove uniqueness and stability.

`WorkspaceRelativePath` is a canonical UTF-8 key, not a host path. It uses `/`
as the only separator and contains one or more nonempty components. Absolute
paths, leading/trailing `/`, `\\`, empty components, `.`, `..`, and NUL are
rejected before apply. Before component validation, any first component whose
first two ASCII bytes are `[A-Za-z]:` is also rejected, covering drive-absolute
and drive-relative forms such as `C:/routes.toml` and `C:routes.toml`. Windows
UNC, rooted, and device prefixes are rejected in both their native backslash
forms and slash-normalized forms by the backslash/leading-slash rules; examples
include `\\server\\share`, `//server/share`, `\\?\\C:\\...`, and
`//?/C:/...`. No percent decoding, Unicode normalization, environment
expansion, or case folding occurs. File-valued response/root fields use this
common grammar; directory-valued root fields use it when nonempty.

`RuleSetPath` adds a required lowercase `.toml` suffix. Its canonical duplicate key is the
accepted byte sequence, so comparison is byte-exact and case-sensitive. A
duplicate is rejected even if the existing rule set is otherwise empty.

These lexical rules are a Local M3 Decision and a `ReferenceGap` relative to
the unavailable engine. The in-memory adapter has no symlinks. A production
filesystem adapter must additionally resolve the workspace root and candidate
parent with platform APIs, reject symlink traversal or any resolved escape, and
use engine/platform collision semantics only after a separate adoption
decision. It must append the already validated components one at a time to an
opened workspace-root handle; passing the original untrusted string to host
`PathBuf::join` is forbidden. M3 tests cover `routes.toml`, `api/v1.toml`, every
rejected component, POSIX absolute and traversal attempts, `C:/...`, `C:...`,
native and slash-normalized UNC/device prefixes, backslashes, wrong extensions,
byte-exact duplicates, and distinct case variants.

### 4. Apply transaction and snapshot refresh

One reducer helper owns configuration edits:

```text
Message → EditTransaction → history preparation → WorkspacePort::apply
        → EditOutcome → replace snapshot → reconcile selection
        → diagnostics/runtime state → record history
```

Apply is atomic from the UI perspective. On `ApplyFailure`:

- the port snapshot is unchanged;
- cached render snapshot and selection are unchanged;
- dirty count, runtime hint, and undo/redo stacks are unchanged; and
- the typed failure becomes a friendly transient failure notice.

On success, the app always adopts the returned full snapshot. `changed_nodes`
is evidence/optimization metadata, not permission to splice mutable snapshot
fragments. Selection remains when its `NodeId` exists. A removed selected
condition falls back to its rule; a removed rule falls back to its rule set; a
removed rule set falls back to the routes empty state. Created-node selection
uses the requested semantic key and its typed receipt. Restore selection and
every older history binding are updated from the complete `NodeRebind` map
before the history entry changes stacks.

### 5. Diagnostics, save, dirty state, and runtime hints

`PortSnapshot::workspace().diagnostics` is the sole durable
workspace-diagnostic source.
`EditOutcome` has no duplicate diagnostics field. `validate()` returns the same
diagnostic set that the next snapshot will expose and may be used for an
explicit refresh; an `ApplyFailure` carries only a transient failure diagnostic
and cannot mutate snapshot diagnostics.

Save results always carry the post-attempt snapshot:

```rust
pub struct SaveOutcome {
    pub snapshot: PortSnapshot,
    pub written_files: Vec<WorkspacePath>,
    pub diffs: Vec<FileDiff>,
    pub unsaved_hint: ReloadHint,
    pub runtime_pending: ReloadHint,
}

pub struct SaveFailure {
    pub snapshot: PortSnapshot,
    pub written_files: Vec<WorkspacePath>,
    pub diffs: Vec<FileDiff>,
    pub failed_file: WorkspacePath,
    pub cause: SaveError,
    pub unsaved_hint: ReloadHint,
    pub runtime_pending: ReloadHint,
}
```

Files are attempted in canonical path byte order. Each file write is atomic;
the whole workspace save is not. Successfully written files become clean and
remain listed if a later file fails. The failed file and all later files remain
dirty. Failure `diffs` include the successful prefix only, and its cumulative
`runtime_pending` adds only that prefix to any previously pending effect.
`unsaved_hint` is recomputed from the failed and later dirty files and reports
their worst remaining effect. The app adopts the returned snapshot and both
phase values on success and failure; retry writes only remaining dirty files.
A fully successful or no-op save returns `unsaved_hint` None. A no-op save also
returns the unchanged snapshot, empty files/diffs, and the existing pending hint
unchanged. The in-memory adapter simulates this contract, including injected
per-file failure, without filesystem writes.

Runtime guidance has two phases owned by `WorkspaceSession`:

- `unsaved_hint` is derived from current dirty diffs against the saved baseline
  after every apply/undo/redo; it can fall back to None when compensation
  removes the triggering diff;
- `runtime_pending` accumulates effects only for successfully written diffs,
  with Restart dominating Reload, and persists after save; and
- `acknowledge_reload` clears Reload only, while `acknowledge_restart` clears
  either value. Reload acknowledgement cannot clear Restart.

Until acknowledgement, `runtime_pending` is intentionally conservative and
monotonic. If saved configuration is edited back to the last runtime-applied
value first, the prompt may be a false positive. Tracking an acknowledged
runtime baseline and recomputing actual divergence is a later refinement, not
an M3 claim.

Every apply/save outcome exposes the current phase value rather than an event
counter. Workspace-derived state therefore follows these rules:

- dirty count is derived from snapshot file flags plus separately scoped
  fallback drafts;
- snapshot diagnostics replace workspace/config diagnostics atomically;
- a failed apply contributes no runtime effect;
- save clears only files the port reports written; and
- no-op save returns no diffs and leaves the existing runtime hint unchanged.

Global Save runs the workspace port first. If it fails, fallback-draft writes
are not attempted. If it succeeds, fallback drafts are attempted in canonical
key order. A later fallback failure does not roll back workspace writes and the
global report identifies both completed and remaining scopes. The app adopts
every returned workspace snapshot. Prototype-local reference gaps never
participate in either save phase or synthesize hints.

`GlobalSaveReport` contains the workspace outcome, written fallback keys, the
optional failed fallback key/cause, and remaining fallback keys. It is returned
for both full and partial completion, so the UI never has to reconstruct save
scope from counters.

### 6. Undo/redo ownership

Undo/redo stays GUI-owned and calls the same port. A `HistoryEntry` records the
semantic before/after values and the current binding needed for compensating
intents; it never mutates snapshots.

Rules:

- record history only after successful apply;
- clear redo after a new successful user edit, not after validation failure;
- undo applies a compensating transaction and moves the entry only on success;
- redo reapplies the forward semantic transaction and moves it only on success;
- failures leave the entry on its original stack and surface diagnostics;
- recreated rules/conditions/rule sets receive new `NodeId`s and every affected
  mutable history binding is updated from the typed `NodeRebind` map;
- selection follows the rebound ID when undo recreates a selected entity; and
- the depth cap remains 50 successful user edits.

Removing a rule or rule set archives its complete semantic subtree plus old IDs
in the history entry. Its inverse is one atomic restore transaction. If any
intent or correlation fails, no candidate state becomes visible, no binding is
updated, and no history entry moves. Ordinary adds use creation keys rather
than old-ID rebinds.

The supported set must include Add/Delete/Move Rule, Add/Remove Rule Set,
rule-core edits, response edits, root-setting edits, and header/body condition
edits. Implementation cannot retain the current silent Add Rule redo no-op.

### 7. Prototype state, session, and external-edit boundary

ReferenceGap controls live in typed app-owned state, never inside the cached
workspace snapshot:

```rust
pub struct PrototypeState {
    pub rule_extras: HashMap<NodeId, RulePrototype>,
    pub trace: TracePrototypeSettings,
}

pub struct RulePrototype {
    pub weight: Option<u32>,
    pub priority: Option<i32>,
}
```

Prototype edits are `HistoryAction::Prototype` entries in the app's unified
50-entry history, with typed before/after values; they do not call the port,
dirty files, emit workspace diagnostics, save, or create runtime hints. Full
snapshot refresh retains entries for surviving rule IDs and drops entries for
rules no longer present, while deletion history keeps removed values in its
archive. An undo restore reinstates archived values using the transaction's
`NodeRebind` map; older prototype-history bindings are rebound by that same map.
Defaults apply to new rules. Trace state has session scope and its own typed
history actions.

One open workspace equals one `WorkspaceSession` and one identity namespace.
Manual reload or switching workspace creates a new session:

- discard old `NodeId` bindings;
- clear undo/redo and adapter diagnostics;
- reset all prototype rule extras and trace settings to fixture defaults;
- cancel pending drafts only through the existing confirmation workflow;
- rebuild selection from the new snapshot, normally at workspace/rule-set
  scope rather than pretending an old ID survived; and
- recompute dirty/runtime state from the new session.

Specifically, reload derives `unsaved_hint` from the new snapshot baseline and
resets `runtime_pending` to None; acknowledgements from the old session cannot
affect the new one.

M3 exposes a `ReloadRequired`/external-change event seam but implements no file
watcher or merge. Later production work must ask before replacing dirty state.
External edits never mutate the current in-memory snapshot behind the port.

### 8. Preparation seam and file boundaries

Before behavior implementation:

1. move all `#[cfg(test)]` modules out of `app.rs` into
   `crates/app/src/app/tests.rs` and descriptively named sibling files below
   `crates/app/src/app/`;
2. preserve test names/behavior and observe the full gates;
3. add only the reducer dispatch seam needed to call the port; and
4. do not move screens, fixtures, routes, or unrelated helpers.

Expected new implementation boundaries are:

```text
crates/model/src/workspace_port.rs
crates/model/src/workspace_port/mapping.rs
crates/model/src/workspace_port/memory.rs
crates/model/src/workspace_port/history.rs
crates/model/src/workspace_port/tests.rs

crates/app/src/app/{workspace_creation,rule_set_creation,rule_duplication,themes}.rs
```

Exact filenames may consolidate after implementation inspection, but any new
tracked file must be disclosed before review. Model code owns pure boundary
types and in-memory semantics; app code owns messages, drafts, selection, and
presentation state. Historical milestone numbers may remain in test module
identifiers when required to preserve test paths, but filenames describe the
behavior under test.

## Contract tests and evidence

Required tests cover:

- every `EditIntent` success, transaction ordering, and representative typed
  failures;
- the complete provenance/mapping tables: all collection states, six URL ops,
  method values, nine header ops, eighteen body ops, response modes, and all
  fourteen root keys with value-shape/range and hint assertions;
- invalid URL/path-op pairing, dotted body paths, header names, exact JSON and
  numeric lexical boundaries, response status/delay, and text/file combinations;
- exhaustive canonical-to-legacy projection and projection/remapping equality
  for all nine header and eighteen body operators, including lowercase header
  names, value-bearing empty strings, presence operations, exponent-form
  numeric input, integer/length values, and typed JSON with differing
  whitespace and object-key order at multiple nesting levels;
- `PortSnapshot` construction proving exactly one ordered condition entry per
  rule, no absent-rule entries, global editable-node ID uniqueness, matching
  canonical/render condition order, and equality to the defined projections;
- stable/unique rule and condition IDs across update, move, snapshot, and save;
- typed creation receipts for duplicate-equal conditions, fresh IDs, and
  complete history rebinding after recreation;
- deletion/recreation of a nonempty rule set, including older history entries
  for rules, equal conditions, and prototype extras inside that subtree;
- injected failure in the middle of compound compensation proving candidate
  state, selection, bindings, and history stacks remain unchanged;
- `changed_nodes`, canonical snapshot diagnostics, dirty flags, unsaved-hint
  recomputation, saved runtime-pending precedence/acknowledgement, failed-apply
  atomicity, and no-op save;
- multi-file save success, failure at first/middle/last file, returned
  post-attempt snapshots/diffs, both runtime phases, retry, and deterministic
  path ordering;
- Global Save workspace-first failure, fallback partial failure, and report
  completeness;
- selection stability and fallback for removal/recreation;
- complete undo/redo round trips for every supported edit family, depth cap,
  redo clearing, and failure stack ownership;
- Add Rule Set positive paths and every lexical rejection, byte-exact duplicate
  and case-sensitive distinction, explicit drive-absolute/drive-relative and
  native/slash-normalized UNC/device prefixes, created selection, undo, and
  rebound redo;
- session reload clearing identity/history and preserving no stale selection;
- prototype state survival across snapshots, pruning, archive/restore/rebind,
  history, defaults, and session reset;
- `ReferenceGap` inventory for weight, priority, strategy parameters, dotted
  object keys, trace settings, path/symlink semantics, and body payload inference;
- exhaustive-match compile coverage so new operators/keys require a decision;
  and
- reducer tests proving configuration messages no longer mutate snapshots
  directly.

Tests must assert the local contract, not claim execution against unavailable
5.10.1 code. When a real artifact is adopted, the same behavior suite becomes
the production-adapter contract suite plus source/version/checksum evidence.

## Implementation sequence

1. Independently accept this RFC and explicitly authorize an implementer.
2. Extract inline app tests mechanically; run and review behavior-neutral gates.
3. Add boundary types, stable condition views, mapping functions, and contract
   tests without changing screens.
4. Implement the in-memory port and transactional apply/save behavior.
5. Replace configuration direct mutations family by family through one reducer
   dispatch helper.
6. Replace undo/redo snapshot mutation with compensating port transactions.
7. Reconcile selection, dirty state, diagnostics, and runtime hints.
8. Correct model/architecture documentation and disclose reference gaps.
9. Run focused, stable, MSRV, lint, audit-cadence, RFC, oracle, inventory, and
   whitespace gates; submit independent implementation review.

## Alternatives considered

### Claim an engine-isomorphic mock model

Rejected. The unavailable executable and reference inconsistencies make that
claim unprovable, while current UI drafts already need different shapes.

### Keep direct snapshot mutation and map only at production integration

Rejected. It leaves M3's core mismatch, unstable condition addressing, broken
redo, and untested conversion semantics in place.

### Depend on an older published apimock-config artifact

Rejected without a separate provenance investigation. An older API would not
prove the documented 5.10.1 editing contract and could force the UI around a
superseded boundary.

### Store full snapshots for undo/redo

Rejected as the production contract. Restoring snapshots bypasses engine
validation, dirty tracking, and runtime hints. Semantic compensating intents
exercise the same apply boundary as user edits.

## Risks and mitigations

| Risk | Mitigation |
|---|---|
| Reference differs from future executable API | Explicit mapping and `ReferenceGap` inventory; fresh adoption review |
| Migration touches oversized reducer | Mechanical test extraction first; family-by-family dispatch replacement |
| New IDs break selection/history | Explicit creation results, rebinding rules, session-scoped tests |
| Mapping loses preserve/clear distinction | Dedicated enum and exhaustive conversion tests |
| Undo compensation fails | Transactional stack ownership; no movement on failed apply |
| Prototype-only controls imply compatibility | Keep outside workspace dirty/effect state and label in docs |
| Structural work expands into M5 | Fixed preparation slice and disclosed file inventory |

## Review questions

1. Is explicit UI mapping the honest choice given the unavailable artifact and
   documented reference gaps?
2. Do semantic creation keys, typed receipts, and bijective subtree rebinds
   remove ambiguity even for equal conditions and older history entries?
3. Are path, collection, URL/method, body/header/response, and root-setting
   conversions deterministic and correctly labeled by provenance?
4. Are diagnostics, partial save, dirty state, and the two runtime-hint phases
   owned unambiguously?
5. Are prototype state and session reload semantics complete?
6. Does atomic compensating-transaction undo/redo satisfy the M3 exit gate?
7. Is the preparation slice narrow enough to avoid premature M5 restructuring?

Creation of this Proposed RFC does not authorize implementation.
